# Emulator source producer

This maintainer entry synchronizes a fixed AOSP source selection and performs one native Emulator build. It is separate from client installation. Complete-client publication remains gated on boot, dependency source and redistribution qualification.

The [source lock](source-lock.xml) contains 75 immutable project revisions derived from the official Emulator build 12560773 manifest. Linux selects 66 projects. The producer verifies each selected checkout and fourteen build-recipe blobs before invoking the pinned build entry. Its own identity is `aiphone-source-d1bfd6eb0ea9-r1`; this selection declares Emulator 35.3.8. It is not corresponding-source evidence for later Google SDK binaries.

Synchronization uses partial cloning and separates network fetch from worktree checkout. Clang expands the recipe's pinned `clang-r487747c` tree; Qt expands the native `linux-x86_64` tree with WebEngine. Both retain project-root files and the selected trees' notices. Unused compiler versions and foreign Qt variants remain unexpanded. Directory identities are checked against the locked commits before selection. All 66 projects remain selected, and both synchronization phases share the original time budget.

The receipt distinguishes initialization, fetch, input selection and checkout, with total/free disk snapshots at each boundary. The initial headroom check is an attempt threshold, not a guarantee that all sources and build outputs fit. The hosted workflow reclaims only unused preinstalled tools on its disposable runner and retains existing SDK licence records. The active disk reserve and process-ownership checks apply throughout synchronization and compilation.

The manually dispatched **Linux Emulator source build** workflow runs isolated unit contracts and real process-ownership regression first. On a disposable GitHub-hosted Linux runner, it verifies the pinned repo tag and launcher, synchronizes source and builds once. The fixed-field result receipt binds the source commit, source inventory and locked inputs. Interrupted work remains unknown and is not automatically replayed.

The optional `retain_source_candidate` input preserves successful output in an unpublished maintainer draft. The retainer verifies the build receipts, seals the ZIP with the shared Rust delivery-volume implementation and checks the uploaded assets against their exact local digests. This source candidate has its own metadata and cannot satisfy complete-client qualification. Redistribution, dependency-source closure and Android boot remain separate gates. Full private build logs and user state are excluded.

The workflow's separate `mode=qualify` consumes the retained SDK pinned in [qualification inputs](../../config/emulator-source-qualification.json). It does not synchronize or compile AOSP again. On a fresh hosted Linux x64 runner with KVM, the Rust `qualify_source_emulator` example admits the SDK, ADB and API 35 image once, creates an independent AVD and checks root, decoded nonblank pixels, Settings/Home key input and data preservation across a cold restart. Its ADB server and emulator use dedicated ports and owned process groups. Success, failure and catchable interruption retire the owned children; an uncatchable runner termination still relies on disposable-host teardown. Neither mode replaces an installed SDK or opens an existing user disk.

The qualification receipt binds its fresh nonce, qualification commit/run and source candidate identity, and records each check separately. Only that fixed-field receipt is retained as an artifact: frames, guest disks and full private command logs stay on the disposable host. A failed child reports its exit status and final 4 KiB of output, with the owned evidence path removed, in the runner console. This fresh instance has no user accounts or application data. `mode=build` retains the existing producer behavior. The qualifier is first tested with `cargo test --locked -p ai-phone-host-runtime --example qualify_source_emulator`; its six Linux cases include malformed/blank images, archive admission, refusal to adopt existing state, real process cleanup and bounded failure diagnostics. A passing SDK run does not certify full phone-use, dependency-source closure, redistribution permission or client installation. The 35.3.8 source candidate is not corresponding-source evidence for the stock 37.2.13 SDK.

The source root derives from the pinned upstream entry's verified checkout location. Output and distribution directories are explicitly bound to the owned build directory. Linux builds run in an owned Xvfb display, with authenticated local sockets and TCP disabled. The upstream embedded-test packager can discover and query that display using `xset`; native tests and test-package creation remain enabled. Display prerequisites and real success, failure and interruption cleanup are checked before source synchronization.

The controller keeps its session leader unreaped until the owned process group has stopped. Display builds terminate the owned group even when its wrapper has already exited: a failed wrapper cannot guarantee child cleanup. The existing two-second termination grace allows Xvfb to release its socket. Short metadata commands retain immediate group cleanup after their leader exits. Final group completion uses the existing ten-second join deadline; an unfinished group remains a cleanup failure. Qualification also exercises failure of the display wrapper's authentication cleanup.

The upstream entry runs with verbose exceptions. Its exit code is separate from distribution-file verification, the source postcheck and artifact hashing. A zero exit followed by a failed postcheck remains unqualified; the receipt records the last verification stage without marking the artifact built. The source postcheck includes a bounded Git status excerpt when rejecting a changed checkout.

Linux SDK package managers run in a private mount namespace. The Rust `release-tools source-sdk-build` entry mounts a writable OverlayFS view of the entire pinned system-images project at its original path, then replaces itself with the original compiler command under the builder's UID, GID and supplementary groups. Nested tools keep their fixed SDK paths; relative links into generic images remain within the same view. The pinned project is neither moved nor copied. Only writes allocate data in `work/sdk-upper`; kernel namespace teardown releases the mount after normal exit, failure or termination of the owned build process group. The existing controller retains its disk reserve and process cleanup contract. No mount is created in the user's host namespace or on an installed device.

The workflow builds and explicitly qualifies this Rust entry before source synchronization. Normal exit, nonzero exit and whole-group cancellation must preserve source bytes, modes, modification times and links. This qualification requires a disposable native Linux filesystem with OverlayFS, `sudo`, `unshare`, `mount` and `setpriv`; failure stops the attempt rather than switching to a full SDK copy. A manual source build must first build `cargo build --locked -p ai-phone-release-tools --bin release-tools` and export `AI_PHONE_SOURCE_RELEASE_TOOLS` as the absolute binary path. The initial `sdk_copy` receipt records zero duplicated source files/bytes for the overlay strategy; it does not measure later copy-up or compiler output usage. A full source build and guest boot remain separate gates.

Mac and Windows maintainers retain the separate writable SDK copy: the producer dereferences shared-image links into `work/sdk`, temporarily aliases the fixed native SDK path and restores the original directory before source verification. An unexpected replacement is preserved for recovery. After an uncatchable process or host termination, retain that dedicated work tree and recover its original directory before reuse. These producers still use first-party Python orchestration; the Linux workspace entry does not complete the remaining pure-Rust migration.

The public receipt retains fixed diagnostic categories from the last 64 KiB of each build log. Traceback locations are limited to the pinned recipe files; exception messages and raw log contents are excluded from the receipt. On build failure, the isolated builder prints separate upstream and producer contexts, each limited to 8 KiB, after replacing builder paths, the runner identity and credential-like lines. Large producer logs reserve up to half that existing budget for the first Git `fatal:`/`error:` lines, so later checkout progress cannot bury the cause; the remainder retains the final summary. Upstream build tails and small logs keep their existing behavior. Full build logs are not uploaded. Missing or malformed diagnostic inputs preserve the original failure.

Run `python3 -B -m unittest -v test_aosp_emulator_producer.py test_linux_bootstrap.py` in this directory for source-contract tests. `qualify_owned_session.py` is a Linux-only regression using owned child processes. It does not access a device, network or source checkout. A real source build requires a fresh dedicated build host with sufficient resources; it is not intended for an active user-data directory.

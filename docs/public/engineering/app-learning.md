# Evidence-backed application experience

AI Phone can retain reusable Android and Linux desktop interaction methods from a completed task and load them when that application is used again. The task ledger and PostgreSQL observations link each saved method to a real action.

The completion verifier may return one optional experience alongside its normal result. This uses the existing verification request and response budget, without a separate learning model call or another device operation. A task that needs input does not publish an automatically inferred method. Invalid optional learning does not turn a valid task result into another execution loop.

The verifier references the tool ledger's exposed `evidence_id` values through `experience.evidence_ids`. Rust binds them to the recorded observations before persistence; the execution tool's `observation_ids` contract stays unchanged. Only completed GUI observation producers from the current request enter this mapping. Unknown events, events from another application and workspace output containing observation-like text cannot supply learning evidence. The verifier reads at most 64 recent ledger results and receives the eligible event IDs and application identities in its schema.

Publication checks the actual task, application, device and observation IDs. A verified method needs at least two observations of that application, including a check after an action. Android uses the observed package name. Linux uses a `linux:` identity derived from the active X11 application's WM_CLASS class, separately from private window/document titles. Missing or invalid identity remains unknown; old observations are not inferred from their titles. Writer, Calc and other applications can have distinct machine classes even when document titles change. Check the current screenshot before acting.

For desktop dialogs, the class follows the actual `WM_TRANSIENT_FOR` parent chain only while process ownership matches. This distinguishes Draw and Calc dialogs even when both use the generic `Soffice` class in one process. The lookup stops at a missing parent, cycle or traversal limit. The active dialog retains its own window and process IDs for input checks.

The verifier must finish after the candidate is recorded. The existing experience publisher then updates a stable Skill for that application. Corrected candidates supersede earlier drafts; the managed section is replaced while manual notes outside it are preserved. Disabled or deleted Skills are respected. The approved-method lookup has a partial index for application/title/time; stored observation identity is retained on action-receipt replay.

The matching [shipped application guide](app-guides.md) is read first, when available; personal experience remains a separate Skill and is not overwritten. Installation and machine-application bindings share one registry.

After a real phone or computer observation identifies the application, the execution loop looks up its enabled experience Skill and reads it before requesting the next model decision. Desktop GUI actions already return an observation; the same receipt supplies after-action evidence without an extra model turn or screenshot request. Commands, cropped images and OCR results do not create a new full-screen observation for learning. The latest unknown/failed observation cannot borrow an older application's identity. The current application is checkpointed. Remaining in the same application does not repeat the lookup, and an already successful read in the task context is reused. Optional recall failure does not pause the device task. The case-insensitive active-Skill index also supports ordinary Skill reads as the collection grows.

Experience contains interaction methods and version limitations, not private messages, contacts, credentials or copied articles. Recalled procedures remain references: current controls, observations and action outcomes determine whether they still apply. Learned guidance cannot expand device permissions or authorize replaying an unknown send.

PostgreSQL stores the Skills and knowledge. The completion audit can also save a reusable cross-application conclusion as a searchable knowledge document. It needs current evidence from at least two applications, including a post-action observation. It uses the same audit request as Skill learning. Repeating a title does not create another document, overwrite edits or recreate a deleted document. The note links back to the source run and audit.
